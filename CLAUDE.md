# Infra: Personal VPS Hosting

Server-level state for the project — the host, its config, and (eventually)
reverse proxy, container orchestration wiring, and scheduled-task
definitions. See the root [`CLAUDE.md`](../CLAUDE.md) for the project-wide
purpose, repo-structure rationale, and Claude's role (tutor / co-designer /
builder) — all of which apply here unchanged.

This is its own git repo, independent of `apps/`. A change spanning infra +
an app is two commits in two repos, by design.

## Deploying an app: filesystem layout and deploy.sh

This project is explicitly a **suite of apps sharing one VPS**, not a
single-app box — the layout and deploy tooling reflect that from the start
rather than being retrofitted once a second app shows up.

- **Each app lives at `/srv/<app-name>` on the server** — a plain `git
  clone` of that app's own repo, mirroring this project's local
  `apps/<app-name>/` layout. Each keeps its own `docker-compose.yml`, its
  own `.env` (hand-created on the server, **never committed, never
  generated by tooling**), and its own private Docker network by default
  (see the Infra Knowledge doc's Compose/networking entries for why that
  isolation is correct, not a limitation, until something needs
  cross-app networking).
- **`apps.conf`** is the registry: one `name=git-url` line per app this box
  deploys. Add a line here when an app is actually ready for a first real
  deploy — not speculatively ahead of that.
- **`deploy.sh <app-name>`** is the one deploy entrypoint, scoped to exactly
  one app per run (it never touches another app's directory). Idempotent:
  clones on first run, `git pull`s on every run after, then
  `docker compose -f docker-compose.yml up -d --build` — the compose file
  is always named explicitly (never a bare `docker compose up`), so a
  tracked `docker-compose.override.yml` in an app's repo (a real, deliberate
  dev-only file — see `apps/diet-helper`) can never accidentally get merged
  into a production deploy. Hard-fails if `.env` is missing rather than
  deploying half-configured. Database migrations are deliberately **not**
  automated by this script yet — the safe ordering (migrate-before-restart
  vs. after) isn't solved, so it's a manual, deliberate step per deploy for
  now.

## Reverse proxy (nginx) — a level above the apps, not a per-app concern

nginx is shared infrastructure serving every app from this project, not
something any single app owns — it belongs here in `infra/`, never in an
app's own repo. Runs **natively on the host** via `apt install nginx`
(not containerized): it's host-level traffic management, not "one more
app," and containerizing it would need `network_mode: host` or
`host.docker.internal` just to reach each app's `localhost` port — real
complexity for zero benefit here.

The shape once it exists: nginx is the *only* thing with a public port
(80/443) open in the firewall; every app's own container instead publishes
to `127.0.0.1:<port>` only (host-reachable, not internet-reachable), and
nginx proxies by hostname to whichever `localhost` port that app runs on.
`nginx/sites/<app-name>.conf` holds each app's routing rule.

## What is NOT set up yet (deliberately, per build-gradually)

- **Docker / Compose on the VPS** — next step.
- **nginx itself** — the layout above is decided; installing and writing
  the first real site config waits for an actual app running in Docker on
  the box to route to.
- **Hetzner Cloud Firewall** (the network-level one, distinct from the
  host's `ufw`) — after Docker + the app define which ports (80/443) need
  opening, so rules aren't guessed.
- **`fail2ban`** — lower priority now that SSH password auth is off; still
  standard, do as its own step.
- **App-level Postgres backup** — no Hetzner whole-disk backup was taken
  (declined at create time), so this is a real near-term gap once diet-helper
  holds data worth keeping.
- **Automated DB migration ordering in `deploy.sh`** — stays a manual step
  per deploy until the safe ordering is actually worked out.
- **cloud-init** — provisioning was done by hand on purpose (learning value);
  revisit automating it once the manual steps are understood.
- **Monitoring / centralized logs / config management (Ansible etc.)** —
  real industry practice at scale or on a team, overkill for one study box.
  Note and revisit if a real need appears.

## Conventions

- **Never edit the live server as a substitute for committing here.** If a
  live fix is genuinely needed, reflect it back into this repo (the runbook
  or a real config file) so the repo and the box don't drift — same rule as
  the root CLAUDE.md's guardrails.
- **Confirm before destructive / infra-affecting commands on the box**
  (`sudo`, service restarts, firewall changes, `reboot`) — a bad change
  here is real downtime once something is deployed.
- The runbook in `docs/` is written to be re-runnable on a fresh VPS from
  scratch — keep it that way when steps change.
